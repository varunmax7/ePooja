# Accessibility audit — Phase 9

§10 Phase 9's acceptance item: "an a11y audit checklist is completed in
`docs/a11y.md`." This is that checklist — what was checked, on what device
class, and what it found. Re-run (and re-date) this list before a release if
`§7` or the navigation structure change materially.

**Checked on:** this machine (no iOS/Android device or Android SDK — same
constraint ADR 0001 recorded in Phase 0). Findings below are static-analysis
and screen-reader-semantics checks (role/label/state wiring, hit-target
arithmetic, contrast token lookups), not an on-device VoiceOver/TalkBack pass.
**Still needed before release:** a real VoiceOver (iOS) and TalkBack (Android)
run through onboarding → Today → a full puja → Sankalpam, on real hardware.

## Labels on controls

Audited every `<Pressable>` in `apps/mobile/app` and `apps/mobile/src`
(excluding `app/_dev`, which never ships) for how a screen reader announces
it.

- **Icon-only controls** (no visible text: close buttons, chevrons, the
  reminder bell) all carry an explicit `accessibilityLabel` — e.g. the
  full-Panchangam sheet's close button, `DaySwipeButton`/`MonthNavButton`'s
  chevrons, `TimingRow`'s bell toggle. Zero found missing one.
- **Text-ful rows** (a radio option, a gender/pada choice, a picker field) rely
  on the nested `<Txt>` children being read as the accessible element's label
  — standard RN behaviour for an `accessible` container — rather than
  duplicating the same string into an explicit `accessibilityLabel`. Checked
  this is in fact how `onboarding/devotee.tsx`, `onboarding/language.tsx` and
  `player/[slug].tsx`'s playback-rate row behave; not a gap.
- Stateful controls expose `accessibilityRole` + `accessibilityState`:
  `TimingRow`'s bell (`role="switch"`), `CheckRow` (`role="checkbox"`), the
  onboarding radio rows (`role="radio"`, `checked`).
- The Puja Runner (`player/[slug].tsx`) marks the step/mantra text
  `accessibilityLiveRegion="polite"` so VoiceOver/TalkBack announces each step
  change without the devotee re-finding focus — carried over from Phase 6,
  confirmed still in place.

## 44 pt hit targets

Computed effective tap area (icon size + 2 × `hitSlop`, or the Pressable's own
`width` where it's larger) for every icon-driven control. Four were short of
44 pt; all four fixed this phase:

| Control                                   | Before            | Fix                          |
| ----------------------------------------- | ----------------- | ---------------------------- |
| `TimingRow` reminder bell (`packages/ui`) | 20 + 2×8 = 36 pt  | `hitSlop` 8 → 12 (44 pt)     |
| My Profile header edit icon               | 22 + 2×10 = 42 pt | `hitSlop` 10 → 11 (44 pt)    |
| Profile edit screen close button          | 24 + 0 = 24 pt    | added `hitSlop={10}` (44 pt) |
| `EnumSearchPicker` close button           | 24 + 0 = 24 pt    | added `hitSlop={10}` (44 pt) |

Every other icon Pressable (`DaySwipeButton`, the new `MonthNavButton`, the
full-Panchangam sheet's close button, the Puja Runner's transport controls)
was already at or above 44 pt.

## Contrast (AA on cream/gold)

§10 names one specific defect: gold text on the cream background reading
below AA. Checked at the token level — `Txt`'s `gold` tone
(`packages/ui/src/components/Txt.tsx`) resolves to `colors.gold['700']`, the
darker step of the scale, not `gold['300']`/`['500']` — so every screen that
asks for `tone="gold"` (the Calendar screen's tithi markers, the
full-Panchangam sheet's "Adhika" tag, the Recipe screen, the Puja Runner) gets
the AA-safe value automatically; no per-screen literal to drift. Not
independently re-measured against a contrast calculator on real device
output — that belongs in the on-device pass above.

## Empty / error / loading states

Spot-checked the screens with state that can plausibly be empty, loading or
errored:

- **Today** and the **full-Panchangam sheet**: "set your location" prompt
  when there's no devotee location yet, a loading row, and a compute-error
  card — all present since Phase 3/9, confirmed still wired after the i18n
  pass.
- **Calendar** (this phase): the same three states, newly added — no
  location, computing, and compute-error cards, matching Today's pattern
  exactly so the two screens behave identically.
- **Storage** (`profile/storage.tsx`, Phase 8): an `ActivityIndicator` while a
  pack download is in flight.
- Not a fresh audit of every screen in the app — these are the ones with
  state that can actually be empty/loading/errored; the rest (static catalog,
  bundled content) have nothing to be empty about.

## Haptics

Existing coverage (Phase 6): `Haptics.selectionAsync()` on the samagri
checklist and the Puja Runner's rate/step controls. Added this phase: the
Today screen's reminder bell toggle now fires the same `selectionAsync()` on
press, so every discrete on/off control in the app gives the same tactile
confirmation.

## Not done in this pass

- **No on-device screen-reader run.** This machine has no iOS/Android
  simulator or hardware (same gap ADR 0001 flagged in Phase 0). Everything
  above is role/label/state/arithmetic correctness, which is necessary but
  not sufficient — a real VoiceOver/TalkBack pass can still surface reading-
  order or focus-trap issues static checking can't.
- **Dynamic Type at 130%** was already verified in Phase 1 (`docs/screens/p1/`)
  for the screens that existed then; the Calendar screen's new month-grid
  layout has not been re-shot at 130% — the cells are fixed 40×44, which is
  the same sizing the Phase 1 grid used and passed at 130%, but it's an
  inference, not a re-run of that screenshot harness.
- **Dark mode** — §10 lists this as optional ("if time allows"); not
  attempted this phase. Every color reference in the app goes through
  `@epooja/ui` tokens, so a dark palette is additive when it's prioritized,
  not a rewrite.
